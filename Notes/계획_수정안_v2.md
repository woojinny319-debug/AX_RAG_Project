> **작성일**: 2026-05-25  
> **근거 문서**: [[프로젝트_검증_삼일AX_벤치마킹]], [[plan]]  
> **핵심 변경**: 단일 K-IFRS RAG → 3개 지식 소스 병렬 조회 구조

## TL;DR

챗봇이 답변할 때 ① K-IFRS 기준 ② 실제 상장사 주석 사례 ③ KAM 보고서 감사 관점을 동시에 제시하는 구조로 전환한다. DART API 활용은 **의미 있고 난이도도 적절**하지만, 라이브 API 호출이 아닌 **사전 캐싱(Pre-cache) 방식**으로 구현해야 데모 안정성이 보장된다. 전체 구현 난이도는 약 **7~10일** 수준으로, Big 4 AI 조직 입사 포트폴리오로 적합한 범위다.

---

## 1. 사용 시나리오 (Why — 목적 구체화)

> "제약·바이오 산업 감사인이 KAM 보고서를 읽다가, 특정 회계처리 사항에 대해 **'K-IFRS 기준은 무엇인지'**, **'경쟁사들은 실제로 어떻게 처리했는지'**, 그리고 **'KAM 보고서는 어떤 감사 위험을 지적하는지'** 를 한 번에 확인하고 싶다."

**예시 질문:**
- "제약사의 연구개발비 자산화 요건은 무엇이며, 주요 제약사들은 어떻게 처리하고 있나요?"
- "바이오시밀러 개발비의 무형자산 인식 기준과 감사상 주의점을 알려주세요."
- "기술이전 계약의 수익인식 시점은 K-IFRS상 어떻게 되나요?"

이 3가지 질문은 KAM 보고서의 3대 핵심 감사사항(연구개발비, 무형자산, 매출인식)과 직접 대응된다.

## 3. DART API 검토

### 3-1. 유의미성: **Yes — 핵심 차별화 요소**

| 관점        | 내용                                             |
| --------- | ---------------------------------------------- |
| 도메인 관련성   | DART 친숙도는 회계법인 AI 조직에서 실무 감각의 신호               |
| 기술적 차별화   | "나는 K-IFRS만 아는 게 아니라, 실제 시장 관행도 확인할 수 있다"는 메시지 |
| 포트폴리오 스토리 | 감사인이 벤치마킹하는 방식 그대로 구현 — 기술과 도메인의 교차점           |
| 면접 활용     | "DART API를 왜 썼나요?" → 감사에서의 피어 컴퍼니 비교 방법론과 직결   |

### 3-2. DART API 기술 구조

```
opendart.fss.or.kr (DART Open API)

[활용 엔드포인트]
① company.json          → 회사 기본정보 (업종, 시장구분)
② list.json             → 특정 회사의 공시 목록 (사업보고서 필터)
③ document.json (간접) → 공시 문서 목록에서 주석 파일 식별
④ 해당 문서 URL 직접 GET → HTML 원문 다운로드 → 주석 텍스트 추출
```

**핵심 문제**: 주석(Notes)은 구조화된 API 응답으로 제공되지 않는다.  
사업보고서 HTML 원문에서 특정 섹션(연결재무제표 주석 → 회계정책)을 파싱해야 한다.

### 3-3. 권고 구현 방식: **Pre-cache + ChromaDB 저장**

```
[1회성 스크립트: dart_ingest.py]
DART API 호출 (상위 5개 제약바이오 기업)
    → HTML 파싱 (BeautifulSoup)
    → LLM으로 관련 주석 섹션 추출
    → ChromaDB 'dart' 컬렉션에 저장
    (메타데이터: company_name, rcpNo, year, section)

[앱 실행 시]
ChromaDB 'dart' 컬렉션 의미론적 검색
    → 관련 회사 주석 텍스트 반환
    → "출처: 삼성바이오로직스 2024 사업보고서 주석 XX"
```

**이 방식의 이점:**
- 데모 중 API 지연/실패 없음 (라이브 API 의존도 제거)
- 실제로는 인제스트 파이프라인과 검색 파이프라인을 분리하는 프로덕션 패턴과 동일
- "왜 pre-cache 했나요?" → 설명 가능한 설계 결정

### 3-4. 대상 기업 (제약바이오 상위)

| 회사명      | 종목코드   | 주요 회계 이슈       |
| -------- | ------ | -------------- |

### 3-5. DART 구현 난이도

| 단계                              | 내용  | 예상 소요      |

## 5. 구현 단계 (Phase별)

### Phase 1 — 기반 RAG 구축 (2~3일)

`rag_engine.py`
- ChromaDB 3개 컬렉션 초기화 (`kifrs`, `kam`, `dart`)
- PDF 로딩 + 조항 단위 청킹 (K-IFRS: 문단 단위, KAM: 섹션 단위)
- **Hybrid Search 구현**: `LangChain EnsembleRetriever` (BM25 + Semantic)
- 검색 결과에 메타데이터(문서명, 문단번호) 포함

### Phase 2 — DART 인제스트 파이프라인 (3~4일)

`dart_ingest.py`
- DART API 호출 → 5개 기업 사업보고서 HTML 수집
- BeautifulSoup으로 주석 섹션 파싱
- GPT-4o-mini로 관련 회계정책 섹션 추출
- ChromaDB `dart` 컬렉션에 저장

### Phase 3 — 앱 통합 + 구조화 출력 (1~2일)

`app.py`
- 3개 컬렉션 병렬 검색 (`asyncio` 또는 `ThreadPoolExecutor`)
- `st.status()`로 3단계 진행 표시: "K-IFRS 검색 중... → 기업 사례 조회 중... → 답변 생성 중..."
- 구조화된 3섹션 출력 (K-IFRS 기준 / 기업 사례 / KAM 관점)
- `.md` 다운로드 (조항 인용 포함)

## 6. 수정 후 난이도 재평가

| 항목       | 이전 계획          | 수정안                      |
| -------- | -------------- | ------------------------ |
| 구현 기간    | ~2일            | 7~10일                    |
| 검색 전략    | Naive Semantic | Hybrid (BM25 + Semantic) |
| 지식 소스    | 1개 (K-IFRS)    | 3개 (K-IFRS + DART + KAM) |
| 인용/출처    | 없음             | 조항 번호 + 기업명 + 보고서 연도     |
| 평가 체계    | 없음             | 3개 샘플 Q&A로 정성 검증         |
| 포트폴리오 수준 | 튜토리얼급          | **Big 4 AI 조직 입사 수준**    |

**기술 면접 대화 시뮬레이션:**
> "왜 3개의 ChromaDB 컬렉션을 분리했나요?" 
> → "K-IFRS(규범적 기준)와 DART(실무 관행)는 검색 시 다른 맥락을 제공하기 때문에 컬렉션을 분리하고, 쿼리 단계에서 병렬로 조회한 후 LLM이 합성하도록 했습니다."

이 답변이 나오는 프로젝트와 안 나오는 프로젝트는 수준이 다르다.
